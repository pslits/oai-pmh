# US-001.06: Observability Contracts

**Feature:** [F-001 — Project Foundation & Shared Contracts](../../F-001_PROJECT_FOUNDATION_AND_SHARED_CONTRACTS.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** S (0.5–1 day)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As a** platform engineer,  
**I want** clearly defined `LoggerInterface` and `MetricsCollectorInterface` contracts in the Observability context,  
**So that** I can integrate with my organization's logging and monitoring infrastructure (ELK, Prometheus, custom solutions) against stable contracts without modifying server internals.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the Observability bounded context exists at `src/Observability/Contract/`,  
      **When** I open `LoggerInterface.php`,  
      **Then** it defines a PHP interface in namespace `OaiPmh\Observability\Contract` that is PSR-3 compatible, providing methods for logging at standard levels (emergency, alert, critical, error, warning, notice, info, debug) with message and context parameters.

- [ ] **Given** the Observability bounded context exists at `src/Observability/Contract/`,  
      **When** I open `MetricsCollectorInterface.php`,  
      **Then** it defines a PHP interface in namespace `OaiPmh\Observability\Contract` with methods for: incrementing counters (by verb, by status), recording histograms (response duration, query duration), and recording cache hit/miss events.

- [ ] **Given** both interfaces are defined,  
      **When** I implement a Prometheus-compatible metrics collector,  
      **Then** the `MetricsCollectorInterface` contract provides sufficient method signatures to record all OAI-PMH operational metrics defined in the technical design (`oaipmh_requests_total`, `oaipmh_response_duration_seconds`, etc.).

- [ ] **Given** both interfaces are defined,  
      **When** I review the docblocks,  
      **Then** every method has a complete docblock, and `LoggerInterface` references PSR-3 compatibility.

### Edge Cases

- [ ] **Given** `LoggerInterface` is PSR-3 compatible,  
      **When** an organization already uses a PSR-3 logger (e.g., Monolog),  
      **Then** wrapping or adapting it to satisfy this interface requires minimal effort — the method signatures align with PSR-3's `LoggerInterface`.

### Error States

- [ ] **Given** the metrics backend is unavailable,  
      **When** a metric recording method is called,  
      **Then** the interface documents that implementations should fail silently (metrics collection must never block or crash the request pipeline, per the Observability context design: "passive, event-driven").

---

## Notes

- **Dependencies**: US-001.01 (namespace scaffolding).
- **Design**: See [SOFTWARE_DESIGN.md](../../../docs/event-storming/SOFTWARE_DESIGN.md) § Context 6: Observability Context — RequestLogger and MetricsCollector aggregates. Observability is passive: it reacts to events and must never block the request/response flow.
- **Constraints**: `LoggerInterface` should extend or align with PSR-3 (`Psr\Log\LoggerInterface`). `MetricsCollectorInterface` is project-specific (no PSR standard for metrics). Both interfaces must not throw exceptions that interrupt request processing.
- **Estimation**: S — two interfaces; `LoggerInterface` follows the well-known PSR-3 pattern, `MetricsCollectorInterface` has 4–5 recording methods.
