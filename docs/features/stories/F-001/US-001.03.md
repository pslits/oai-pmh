# US-001.03: Metadata Format Plugin Contract

**Feature:** [F-001 — Project Foundation & Shared Contracts](../../F-001_PROJECT_FOUNDATION_AND_SHARED_CONTRACTS.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** S (0.5–1 day)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As a** plugin developer,  
**I want** a clearly defined `MetadataFormatPluginInterface` contract in the MetadataSerialization context,  
**So that** I can implement custom metadata format plugins (e.g., DataCite, MARC) against a stable interface without understanding the server's internal architecture.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the MetadataSerialization bounded context exists at `src/MetadataSerialization/Contract/`,  
      **When** I open `MetadataFormatPluginInterface.php`,  
      **Then** it defines a PHP interface in namespace `OaiPmh\MetadataSerialization\Contract` with methods for: serializing a record to an XML metadata fragment, reporting the metadata prefix, returning the schema URL, and returning the metadata namespace.

- [ ] **Given** the interface is defined,  
      **When** I implement a custom metadata format (e.g., DataCite),  
      **Then** I only need to implement the interface methods — no base class inheritance or internal server knowledge is required.

- [ ] **Given** the interface defines a `serialize` method,  
      **When** I check its signature,  
      **Then** it accepts a record (via `RecordInterface` from Repository context) and returns a well-formed XML string fragment.

- [ ] **Given** the interface is defined,  
      **When** I review the docblocks,  
      **Then** every method has a complete docblock referencing the OAI-PMH 2.0 specification § 3.4 (metadataPrefix, schema, metadataNamespace) and explaining the contract.

### Edge Cases

- [ ] **Given** a record does not support a particular metadata format,  
      **When** I check the interface,  
      **Then** it includes a `supports` method that allows plugin developers to indicate per-record format availability (enabling format-specific record filtering).

### Error States

- [ ] **Given** a plugin fails to serialize a record (e.g., missing required fields),  
      **When** serialization is attempted,  
      **Then** the interface documents (via `@throws`) the expected exception type so callers can handle serialization failures gracefully.

---

## Notes

- **Dependencies**: US-001.01 (namespace scaffolding). Loosely coupled to US-001.02 (`RecordInterface` is referenced as a parameter type).
- **Design**: See [SOFTWARE_DESIGN.md](../../../docs/event-storming/SOFTWARE_DESIGN.md) § Context 3: Metadata Serialization Context — MetadataFormat aggregate. OAI-PMH spec requires `oai_dc` (Dublin Core) as the minimally recommended format; this interface enables that and any additional format plugins.
- **Constraints**: Interface must not depend on any infrastructure classes. Methods must use domain value objects (`MetadataPrefix`, `MetadataNamespace`) where appropriate. Must enable third-party Composer package plugins.
- **Estimation**: S — one interface with 5–6 methods; signature design is well-guided by the OAI-PMH spec.
