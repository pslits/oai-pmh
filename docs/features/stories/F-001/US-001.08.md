# US-001.08: Server Entry Point and Architecture Decision Records

**Feature:** [F-001 — Project Foundation & Shared Contracts](../../F-001_PROJECT_FOUNDATION_AND_SHARED_CONTRACTS.md)  
**Implementation Plan:** [Phase 0.4 — Architecture Decision Records](../../../docs/IMPLEMENTATION_PLAN.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** S (0.5–1 day)  
**Status:** Draft  
**Date:** February 19, 2026  

---

## Story

**As a** core developer,  
**I want** a working CLI entry point for the server and an Architecture Decision Records directory with a README, a reusable template, and the eight planned ADR stubs from the Software Design session,  
**So that** I know where the server process starts, and every key architectural decision is documented, discoverable, and consistently formatted before implementation of those decisions begins.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the project root contains a `bin/` directory,  
      **When** I open `bin/oaipmh-server`,  
      **Then** it is a valid PHP script with the project's standard file header, `declare(strict_types=1)`, Composer autoloader inclusion, and a clear placeholder comment indicating it is the future server entry point.

- [ ] **Given** the entry point script exists,  
      **When** I check the `bin` key in `composer.json`,  
      **Then** `bin/oaipmh-server` is listed, making it available as a Composer-installed binary.

- [ ] **Given** the project root has a `docs/` directory,    
      **When** I look for `docs/adr/`,  
      **Then** the directory exists and contains a `README.md` explaining the purpose of ADRs, the file naming convention (`ADR-00{N}-{slug}.md`), a link to the ADR template, and a table listing all eight planned ADRs with their numbers and titles.

- [ ] **Given** the ADR directory is set up,  
      **When** I want to record a new architectural decision,  
      **Then** a template file `docs/adr/adr-template.md` exists with sections: Title, Status, Date, Deciders, Context (with Forces at Play), Decision (with Chosen Approach and Implementation Details), Alternatives Considered, Consequences, Compliance, Implementation Guidance, Validation, and References.

- [ ] **Given** the eight ADRs listed in Implementation Plan § 0.4 are identified,  
      **When** I check `docs/adr/`,  
      **Then** each of the following stub files exists, created from the template with status "Proposed" and the Context section pre-filled from the Software Design session:  
      | File | Decision |
      |------|----------|
      | `ADR-001-token-format.md` | Token format: JWT vs. Redis UUID vs. encoded state |
      | `ADR-002-schema-mapping.md` | Schema mapping: YAML DSL definition |
      | `ADR-003-database-abstraction.md` | Database abstraction: Doctrine DBAL vs. PDO direct |
      | `ADR-004-cache-backend.md` | Cache backend: Redis as primary, file as fallback |
      | `ADR-005-middleware-pipeline.md` | Middleware pipeline: PSR-15 middleware stack |
      | `ADR-006-xml-generation.md` | XML generation: DOMDocument vs. XMLWriter vs. SimpleXML |
      | `ADR-007-configuration-loader.md` | Configuration: Symfony Config component vs. custom YAML loader |
      | `ADR-008-php-version-constraints.md` | PHP version minimum and dependency constraints |

- [ ] **Given** each ADR stub file exists,  
      **When** I review its content,  
      **Then** it follows the project's ADR template structure, has a meaningful title, and the Context section describes the problem the decision addresses.

### Edge Cases

- [ ] **Given** the `bin/oaipmh-server` entry point is a placeholder,  
      **When** I execute it from the command line (`php bin/oaipmh-server`),  
      **Then** it outputs a clear message indicating the server is not yet implemented and exits with code 0 (clean exit, no errors).

- [ ] **Given** the project already has a `.github/adr/adr-template.md`,    
      **When** the `docs/adr/adr-template.md` is created,  
      **Then** it matches or references the canonical template in `.github/adr/` to avoid template drift.

### Error States

- [ ] **Given** the Composer autoloader has not been generated (no `vendor/autoload.php`),  
      **When** I execute `php bin/oaipmh-server`,  
      **Then** the script detects the missing autoloader and outputs a helpful error message directing the developer to run `composer install`, then exits with a non-zero code.

- [ ] **Given** a contributor creates a new ADR without following the naming convention,    
      **When** they consult `docs/adr/README.md`,  
      **Then** the README provides the exact naming pattern (`ADR-00{N}-{slug}.md`), an example, and a step-by-step guide for adding a new ADR.

## Notes

- **Dependencies**: US-001.01 (namespace scaffolding creates the `docs/` directory structure); the `bin/` directory already exists with the placeholder script — verify and update it to meet the criteria above.
- **Design**: The eight ADRs map directly to [Implementation Plan § 0.4](../../../docs/IMPLEMENTATION_PLAN.md) and originate from the key decisions identified in the [Software Design](../../../docs/event-storming/SOFTWARE_DESIGN.md) Event Storming session. The template follows the project's extended ADR format in [`.github/adr/adr-template.md`](../../../../.github/adr/adr-template.md), which expands the [Michael Nygard ADR format](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) with Compliance, Implementation Guidance, and Validation sections. The `bin/oaipmh-server` entry point must carry the project's standard PHP file header and follow PSR-12.
- **Constraints**: ADR stubs must have status "Proposed". Full decision rationale will be filled in as each decision is made during the relevant implementation phase — the goal here is to create the scaffolding and seed the context, not to make the decisions.
- **Estimation**: S — verify/update one bin script, register it in `composer.json`, create one `docs/adr/` README, one template, and eight stub files with pre-filled context sections.
