# US-002.05: Immutable Configuration After Construction

**Feature:** [F-002 — Configuration Management](../../F-002_CONFIGURATION_MANAGEMENT.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** S (0.5 day)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As the** server application,  
**I want** the Configuration aggregate to be immutable after construction,  
**So that** no component can accidentally or intentionally modify the configuration at runtime, guaranteeing predictable, consistent behaviour for the lifetime of the process.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the Configuration aggregate has been successfully constructed (loaded, merged, substituted, validated),  
      **When** I inspect the class definition,  
      **Then** it has no public setter methods, no `set()`, `update()`, or `modify()` methods — only getters and query methods.

- [ ] **Given** a fully constructed Configuration instance,  
      **When** I retrieve a configuration section or value,  
      **Then** the returned data is a copy (or immutable view) — modifying the returned array does not alter the Configuration's internal state.

- [ ] **Given** the Configuration class,  
      **When** I check its constructor visibility and class declaration,  
      **Then** the class is declared `final` to prevent subclasses from adding mutable behaviour.

### Edge Cases

- [ ] **Given** a consuming context retrieves a section array via `getSection()`,  
      **When** the consumer modifies the returned array (e.g., `$section['host'] = 'evil.com'`),  
      **Then** calling `getSection()` again returns the original, unmodified values — internal state is not affected.

### Error States

- [ ] **Given** the Configuration aggregate is constructed,  
      **When** any code attempts to modify it at runtime (e.g., via reflection or by calling a method that would alter state),  
      **Then** the Configuration's design prevents mutation — there are no code paths that can change its internal data after construction.

---

## Notes

- **Dependencies**: US-002.01 (the Configuration class must exist).
- **Design**: See [SOFTWARE_DESIGN.md](../../../event-storming/SOFTWARE_DESIGN.md) § Context 7: Configuration Context — "Immutable after validation — read-only for the lifetime of the process". Also see Architecture Notes: "Configuration immutable after startup — Simple, predictable, no race conditions."
- **Constraints**: The `final` keyword on the class declaration, `private readonly` properties (PHP 8.1+) or private properties with no setters, and returning array copies from getters are the primary enforcement mechanisms.
- **Pattern**: Follows the same immutability pattern as the existing domain value objects (e.g., `BaseURL`, `DeletedRecord`).
- **Estimation**: XS–S — primarily a design constraint enforced by class structure; verify no mutation paths exist.
