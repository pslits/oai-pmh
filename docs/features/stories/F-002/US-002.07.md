# US-002.07: Environment-Specific Configuration Precedence

**Feature:** [F-002 — Configuration Management](../../F-002_CONFIGURATION_MANAGEMENT.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** M (1–1.5 days)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As a** DevOps engineer deploying the server across multiple environments (development, staging, production),  
**I want** environment-specific configuration files to override default settings with a clear, predictable precedence order,  
**So that** I can maintain a shared baseline configuration and override only what differs per environment without duplicating the entire configuration file.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** a `config/default.yaml` file defines `cache.driver: file` and a `config/production.yaml` file defines `cache.driver: redis`,  
      **When** the server starts in the `production` environment,  
      **Then** the resolved `cache.driver` value is `redis` (environment-specific file overrides the default).

- [ ] **Given** the precedence order is `default.yaml < environment.yaml < environment variables`,  
      **When** `default.yaml` sets `database.port: 3306`, `staging.yaml` sets `database.port: 3307`, and env var `${DATABASE_PORT}` resolves to `3308`,  
      **Then** the final resolved value of `database.port` is `3308` (environment variables always win).

- [ ] **Given** a `config/default.yaml` file and a `config/development.yaml` file both exist,  
      **When** the server starts with the `development` environment indicator,  
      **Then** `default.yaml` is loaded first, then `development.yaml` is merged on top, overriding any duplicate keys.

- [ ] **Given** the environment is determined by an environment variable (e.g., `APP_ENV=production`) or a startup parameter,  
      **When** the Configuration aggregate constructs,  
      **Then** it loads `config/default.yaml` and then `config/<APP_ENV>.yaml` if the file exists.

### Edge Cases

- [ ] **Given** the environment is set to `staging` but `config/staging.yaml` does not exist,  
      **When** the server starts,  
      **Then** only `config/default.yaml` is loaded — the absence of an environment-specific file is not an error.

- [ ] **Given** the environment-specific file adds a new section not present in `default.yaml`,  
      **When** configuration is merged,  
      **Then** the new section is added to the configuration (merge is additive, not replacement).

- [ ] **Given** a deeply nested key is overridden in the environment-specific file (e.g., `security.rate_limiting.by_ip.requests_per_minute: 120`),  
      **When** files are merged,  
      **Then** only that specific key is overridden — sibling keys in the same nested structure retain their default values.

### Error States

- [ ] **Given** `config/default.yaml` does not exist,  
      **When** the server starts,  
      **Then** a `ConfigurationLoadException` is thrown because the base configuration file is mandatory.

- [ ] **Given** environment-specific YAML has invalid syntax,  
      **When** the server starts,  
      **Then** a `ConfigurationLoadException` is thrown with a message identifying the problematic file: e.g., `"Failed to parse configuration file: config/production.yaml"`.

## Notes

- **Dependencies**: US-002.01 (YAML loading), US-002.02 (default merging), US-002.03 (env var substitution). This story integrates all three into a layered precedence chain.
- **Design**: See [REPOSITORY_SERVER_REQUIREMENTS.md](../../../REPOSITORY_SERVER_REQUIREMENTS.md) § 2.5.2 — "Config file precedence: default.yaml < environment.yaml < env vars".
- **Precedence chain** (lowest to highest priority):
  1. `config/default.yaml` — project-provided defaults (always loaded)
  2. `config/<environment>.yaml` — environment-specific overrides (optional)
  3. Environment variables via `${VAR}` substitution — highest priority, applied last
- **Environment detection**: Use `APP_ENV` environment variable (default: `development` if not set).
- **Constraints**: Deep merge at every layer. The merge logic from US-002.02 is reused here for layering multiple files.
- **Estimation**: M — requires loading multiple files, merging in order, handling missing optional files, and integrating with env var substitution.
