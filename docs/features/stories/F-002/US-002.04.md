# US-002.04: Validate Configuration at Startup

**Feature:** [F-002 — Configuration Management](../../F-002_CONFIGURATION_MANAGEMENT.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** M (1–2 days)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As the** server application,  
**I want** the complete configuration to be validated at startup and all errors reported at once,  
**So that** misconfigurations are caught before the server begins serving requests and the administrator can fix every issue in a single pass.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the configuration (after YAML loading, default merging, and env var substitution) contains all required fields with valid values,  
      **When** validation runs,  
      **Then** validation passes and the Configuration aggregate is fully constructed and ready for use.

- [ ] **Given** the `repository` section has all required fields (`name`, `baseUrl`, `adminEmail`, `deletedRecord`, `granularity`),  
      **When** validation runs,  
      **Then** the `repository` section passes validation without errors.

- [ ] **Given** the `database` section has all required fields (`driver`, `host`, `port`, `name`, `user`, `password`),  
      **When** validation runs,  
      **Then** the `database` section passes validation without errors.

- [ ] **Given** the `metadata_formats` section contains at least one format with `prefix`, `plugin`, and `enabled: true`,  
      **When** validation runs,  
      **Then** the section passes validation, confirming the server can disseminate at least one metadata format.

### Aggregated Error Reporting

- [ ] **Given** the configuration is missing `repository.name`, `database.host`, and `logging.level` simultaneously,  
      **When** validation runs,  
      **Then** a single `ConfigurationValidationException` is thrown containing ALL three errors — not just the first one found.

- [ ] **Given** a `ConfigurationValidationException` is thrown,  
      **When** I inspect the exception,  
      **Then** it provides a method (e.g., `getErrors(): array`) that returns a list of individual error messages, each identifying the section and field that failed.

- [ ] **Given** a `ConfigurationValidationException` with multiple errors,  
      **When** I call `getMessage()` on the exception,  
      **Then** the message is a human-readable summary listing all errors, e.g.:  
      ```
      Configuration validation failed with 3 errors:
        - repository.name: Required field is missing.
        - database.host: Required field is missing.
        - logging.level: Required field is missing.
      ```

### Required Fields Validation

- [ ] **Given** the following sections and their required fields:  
      | Section | Required Fields |
      |---------|----------------|
      | `repository` | name, baseUrl, adminEmail, deletedRecord, granularity |
      | `database` | driver, host, port, name, user, password |
      | `mapping` | record_table, identifier_field, datestamp_field |
      | `metadata_formats` | at least one entry with prefix, plugin, enabled |
      | `resumption` | page_size, token_lifetime |
      | `cache` | driver |
      | `security` | force_https |
      | `logging` | level, path |  
      **When** any required field is missing from a required section,  
      **Then** a validation error is added for each missing field with the format `"section.field: Required field is missing."`.

### Edge Cases

- [ ] **Given** a required section is present but contains only unrecognised keys (typos, e.g., `databse.hots`),  
      **When** validation runs,  
      **Then** the required fields within that section are reported as missing (unknown keys are ignored; no "unknown key" warnings in MVP).

- [ ] **Given** all required fields are present but an entire optional section (e.g., `monitoring`) is absent,  
      **When** validation runs,  
      **Then** validation passes — optional sections are not required.

### Error States

- [ ] **Given** the configuration has zero required fields present (worst case),  
      **When** validation runs,  
      **Then** a `ConfigurationValidationException` is thrown listing every single missing required field across all required sections.

## Notes

- **Dependencies**: US-002.01 (YAML loading), US-002.02 (defaults merged), US-002.03 (env vars substituted). Validation runs after all three processing steps are complete.
- **Design**: See [SOFTWARE_DESIGN.md](../../../event-storming/SOFTWARE_DESIGN.md) § Context 7: Configuration Context — command "Validate Configuration".
- **Files**:
  - `src/Configuration/Exception/ConfigurationValidationException.php`
  - Updates to `src/Configuration/Aggregate/Configuration.php`
  - Updates to `tests/Configuration/Aggregate/ConfigurationTest.php`
- **Constraints**: Validation must be exhaustive (report ALL errors, not fail-on-first). The validator iterates all required sections and fields, collects errors, and throws once with the full list.
- **Future**: Value-format validation (e.g., valid URL for `baseUrl`, valid email for `adminEmail`) can be added in a follow-up story or later sprint. MVP validates field presence only.
- **Estimation**: M — requires defining the full required-fields map, iterating all sections, collecting errors, and building the exception with aggregated messages.
