# US-002.08: Sample and Default Configuration Files

**Feature:** [F-002 — Configuration Management](../../F-002_CONFIGURATION_MANAGEMENT.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** S (0.5–1 day)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As a** developer or repository administrator setting up the server for the first time,  
**I want** a fully documented sample configuration file and a default configuration file provided with the project,  
**So that** I know what configuration options are available, what each option does, and what sensible defaults are applied — without having to read source code.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the project repository,  
      **When** I look in the `config/` directory,  
      **Then** I find `config.yaml.example` — a comprehensive reference file with all supported configuration keys, inline comments explaining each option, and example values.

- [ ] **Given** the project repository,  
      **When** I look in the `config/` directory,  
      **Then** I find `default.yaml` — a file containing all default values for optional fields, used as the base layer in the precedence chain (US-002.07).

- [ ] **Given** the `config.yaml.example` file,  
      **When** I read it,  
      **Then** every configuration section (`repository`, `database`, `mapping`, `metadata_formats`, `resumption`, `cache`, `security`, `logging`, `monitoring`) is documented with:
      - A comment block explaining the section's purpose
      - Every supported key with its type, default value (if optional), and description
      - Example values that form a valid, working configuration

- [ ] **Given** the `config/default.yaml` file,  
      **When** I review its contents,  
      **Then** it contains only optional fields with their default values (e.g., `resumption.page_size: 100`, `cache.driver: file`, `security.force_https: false`, `logging.level: info`) and does NOT contain required fields.

- [ ] **Given** an administrator copies `config.yaml.example` to `config.yaml` and fills in the required fields,  
      **When** the server starts,  
      **Then** the configuration loads, validates, and the server starts successfully — the example file is a working starting point.

### Edge Cases

- [ ] **Given** the `default.yaml` file,  
      **When** it is loaded by the Configuration aggregate,  
      **Then** it is valid YAML that parses without errors and all its values are compatible with the validation rules from US-002.04.

### Error States

- [ ] **Given** the `config.yaml.example` file is used as-is without editing (required fields still have placeholder values),  
      **When** the server starts,  
      **Then** a `ConfigurationValidationException` is thrown — placeholder values are clearly marked as needing replacement (e.g., `"YOUR_DATABASE_HOST"`, `${DB_PASSWORD}`).

## Notes

- **Dependencies**: US-002.04 (validation rules must be finalized so the example file can demonstrate what's required).
- **Design**: See [REPOSITORY_SERVER_REQUIREMENTS.md](../../../REPOSITORY_SERVER_REQUIREMENTS.md) § 2.5.1 — "Sample configuration files provided".
- **Files**:
  - `config/config.yaml.example` — fully documented reference file
  - `config/default.yaml` — default values for optional fields
- **Example `config.yaml.example` sections**:
  ```yaml
  # =================================================================
  # OAI-PMH Repository Server Configuration
  # =================================================================
  # Copy this file to config.yaml and fill in your values.
  # Lines marked [REQUIRED] must be provided.
  # Lines marked [OPTIONAL] have default values shown.
  # =================================================================

  # Repository Identity (OAI-PMH Identify response)
  repository:
    name: "Your Repository Name"        # [REQUIRED] Human-readable name
    baseUrl: "https://example.org/oai"   # [REQUIRED] OAI-PMH base URL
    adminEmail: "admin@example.org"      # [REQUIRED] Administrator email
    deletedRecord: "persistent"          # [REQUIRED] no|transient|persistent
    granularity: "YYYY-MM-DDThh:mm:ssZ"  # [REQUIRED] Date granularity
  ```
- **Constraints**: Example file must use environment variable placeholders for all sensitive values (passwords, keys). Default file must be minimal — only optional fields with defaults.
- **Estimation**: S — primarily documentation work; requires understanding of all validation rules.

| **N** — Negotiable | ✅ | Comment style, example values, and level of documentation are negotiable. |
| **V** — Valuable | ✅ | Dramatically reduces time-to-first-deployment — administrators don't need to guess at configuration options. |
| **E** — Estimable | ✅ | Two YAML files with comments; content fully determined by the configuration schema. |
| **S** — Small | ✅ | S-sized; two files, primarily documentation. |
| **T** — Testable | ✅ | Both files parse as valid YAML. Example file (with required fields filled) produces a valid configuration. Default file merges correctly with user config. |
