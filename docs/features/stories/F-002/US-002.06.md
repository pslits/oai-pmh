# US-002.06: Read-Only Section Access

**Feature:** [F-002 — Configuration Management](../../F-002_CONFIGURATION_MANAGEMENT.md)  
**Priority:** MVP (MUST HAVE)  
**Estimation:** S (0.5–1 day)  
**Status:** Draft  
**Date:** February 18, 2026  

---

## Story

**As a** developer building a feature in any bounded context (Repository, Protocol, Metadata Serialization, etc.),  
**I want** to retrieve a specific configuration section by name via `getSection(string $name): array`,  
**So that** my context receives only the configuration it needs and I don't have to parse or understand the entire configuration structure.

---

## Acceptance Criteria

### Happy Path

- [ ] **Given** the Configuration aggregate is fully constructed and contains a `database` section with keys `driver`, `host`, `port`, `name`, `user`, `password`,  
      **When** I call `$config->getSection('database')`,  
      **Then** it returns an associative array with exactly those keys and their configured values.

- [ ] **Given** the configuration contains all standard sections (`repository`, `database`, `mapping`, `metadata_formats`, `resumption`, `cache`, `security`, `logging`, `monitoring`),  
      **When** I call `getSection()` for each section name,  
      **Then** each call returns the correct section data as an associative array.

- [ ] **Given** the `getSection()` method is called,  
      **When** I check the method signature,  
      **Then** it matches the contract defined in `ConfigurationInterface` (from F-001/US-001.07): `getSection(string $name): array`.

- [ ] **Given** a consuming context (e.g., Repository Context) receives a section array,  
      **When** it reads values from the array,  
      **Then** the values reflect the final resolved configuration (after YAML loading, default merging, env var substitution, and validation).

### Edge Cases

- [ ] **Given** the configuration contains a section with nested sub-sections (e.g., `security.rate_limiting.by_ip`),  
      **When** I call `getSection('security')`,  
      **Then** the returned array preserves the full nested structure, including nested arrays.

- [ ] **Given** the `monitoring` section was populated entirely from default values (administrator did not specify it),  
      **When** I call `getSection('monitoring')`,  
      **Then** the returned array contains the default values — the caller cannot distinguish between explicit and default values.

### Error States

- [ ] **Given** the Configuration aggregate is constructed,  
      **When** I call `getSection('nonexistent_section')` for a section name that does not exist in the configuration,  
      **Then** an `\InvalidArgumentException` is thrown with a message: e.g., `"Unknown configuration section: 'nonexistent_section'. Available sections: repository, database, mapping, ..."`.

## Notes

- **Dependencies**: US-002.05 (immutability — returned arrays must be defensive copies to maintain immutability).
- **Design**: See [SOFTWARE_DESIGN.md](../../../event-storming/SOFTWARE_DESIGN.md) § Context 7: Configuration Context — command "Get Section". Also see the Cross-Context Integration table showing that all contexts receive settings via "Get Section".
- **Consumers**:
  | Section | Consuming Context |
  |---------|------------------|
  | `repository` | Repository Context, Protocol Context |
  | `database` | Repository Context |
  | `mapping` | Repository Context |
  | `metadata_formats` | Metadata Serialization Context |
  | `resumption` | Flow Control Context |
  | `cache` | All Contexts |
  | `security` | Access Control Context |
  | `logging` | Observability Context |
  | `monitoring` | Observability Context |
- **Constraints**: Must implement the `ConfigurationInterface::getSection()` contract. Returns a plain PHP array (not an object) for simplicity in MVP. Consumers should not depend on the concrete `Configuration` class — only on `ConfigurationInterface`.
- **Estimation**: S — one method implementation plus one error path; straightforward.
